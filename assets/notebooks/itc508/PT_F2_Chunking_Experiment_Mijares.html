Component I: Vector Indexing and Embedding¶

PhilHealth Circular 2024-0037 supplies the family-planning benefit and claims information used in the BenepiKnow retrieval experiment. Component I prepares the source text, divides the extracted page text into chunks, creates embeddings with the SEA-LION model, and stores the vectors in FAISS for semantic retrieval. Component II loads the Qwen tokenizer, the system prompt, and the answer generation functions. Both components are the same code used in PT-F1, so the embedding model, generation model, prompt, and retrieval settings do not change in Part 2.

PT-F2 tests which chunk size and overlap give the best retrieval for the circular. In this notebook, a configuration means one pair of settings, the chunk size in characters and the overlap in characters. Component III first runs the PT-F1 baseline configuration of 1,000-character chunks and 200-character overlap, and saves its results as the reference. It then runs 12 more configurations, named C1 to C12. The activity gives the first five, C1 300/0, C2 300/30, C3 300/60, C4 500/0, and C5 500/50, where each pair is chunk size over overlap. The remaining seven, C6 to C12, were chosen for this dataset and are explained in the configuration cell.

Every configuration builds a new FAISS index and retrieves the top 3 chunks for the same nine test questions. Top-K, the number of chunks returned per question, stays at 3 the whole time. The retrieved chunks are compared with evidence units, which are the exact passages or fee table rows that a correct answer needs, written down before the experiment. Three scores come out of this comparison. Precision@3 is the share of the 3 retrieved chunks that contain evidence. Recall@3 is the share of the needed evidence units that the 3 chunks found. MRR@3 shows how high the first useful chunk appears in the ranking, where 1.0 means it was always the first chunk.

The Part 1 test runs for chunk size, overlap, and Top-K, and the interactive question session, are not included here because PT-F2 replaces them with the controlled experiment. They remain in the PT-F1 notebook.

# Send paced requests without displaying the authorization header.
def sea_lion_request(endpoint, payload=None):
    global _last_api_request
    for attempt in range(3):
        if _last_api_request is not None:
            delay = API_INTERVAL_SECONDS - (time.monotonic() - _last_api_request)
            if delay > 0:
                time.sleep(delay)
        _last_api_request = time.monotonic()
        try:
            response = requests.request(
                "GET" if payload is None else "POST",
                f"{API_BASE_URL}/{endpoint}",
                headers={"Authorization": f"Bearer {SEA_LION_API_KEY}"},
                json=payload,
                timeout=120,
            )
        except requests.RequestException:
            raise RuntimeError("SEA-LION connection failed; check the Colab connection and retry.") from None

        # Temporary rate or server errors receive a limited retry.
        if response.status_code in (429, 502, 503, 504) and attempt < 2:
            time.sleep(15 * (attempt + 1))
            continue
        if not response.ok:
            raise RuntimeError(
                f"SEA-LION HTTP {response.status_code}; check model access, request limits, and API settings."
            )
        return response.json()

Creating the Document Chunks¶

The create_chunks function divides the extracted PDF page text into overlapping sections while keeping each section linked to the original PDF page. Processing pages separately allows later results to report a specific page number. The parameters pages, chunk_size, and chunk_overlap make the function use the extracted records and current settings rather than fixed values inside the function. chunks = [] collects the records, and chunk_id = 0 starts a unique identifier for each stored chunk.

step_size = chunk_size - chunk_overlap determines how far the next starting position moves. For each page, the function reads the page number and text, then sets start = 0 so processing begins at the first character. The while condition keeps slicing until the starting position reaches the end of the page. end = start + chunk_size sets the upper boundary, while page_text[start:end].strip() extracts the text and removes edge whitespace.

With the current settings, the first slice starts at character 0 and ends before character 1,000; the second starts at character 800 and ends before character 1,800. The shared 200-character range keeps some text around the boundary available to both chunks. A slice near the page end can be shorter because Python slicing stops at the available text. The function slices by character position and does not search for complete sentences, so overlap helps preserve context without guaranteeing a complete idea in every chunk.

if chunk_text prevents empty slices from becoming chunk records. chunks.append stores the identifier, page, and text together because retrieval needs both the content and source details. chunk_id += 1 gives the next stored record a different identifier, and start += step_size moves the slice forward while keeping the planned overlap.

return chunks sends the list back to the calling cell after every page has been processed. The assignment chunks = create_chunks(pages, CHUNK_SIZE, CHUNK_OVERLAP) actually runs the function; the earlier def statement only defines the steps. The resulting list is checked in the next cell.

# Page records and size settings are accepted for overlapping character-based chunking.
def create_chunks(
    pages,
    chunk_size,
    chunk_overlap
):
    """
    Split each page into character-based chunks.

    Chunking is performed independently for each page.
    Overlap is maintained between consecutive chunks
    from the same page.
    """

    # The chunk list stores text and source details for embedding and retrieval.
    chunks = []

    # Chunk identifiers start at zero so stored records can be distinguished.
    chunk_id = 0

    # Subtracting overlap gives an 800-character advance with the current settings.
    step_size = chunk_size - chunk_overlap

    # Each page is chunked separately to keep a clear source reference.
    for page_data in pages:

        # The source page number is kept for tracing retrieved text.
        page_number = page_data["page"]

        # Repeated whitespace becomes one space to reduce irregular spacing before chunking.
        page_text = page_data["text"]

        # Each page starts at character zero so no leading text is skipped.
        start = 0

        # Slicing continues while the start position remains inside the page text.
        while start < len(page_text):

            # The end boundary limits the slice to the configured chunk size.
            end = start + chunk_size

            # The slice keeps the current text section and removes edge whitespace.
            chunk_text = page_text[start:end].strip()

            # Empty slices are excluded from the chunk records.
            if chunk_text:

                # The identifier, source page, and text are kept in one chunk record.
                chunks.append({
                    "chunk_id": chunk_id,
                    "page": page_number,
                    "text": chunk_text
                })

                # The next stored chunk receives a different identifier.
                chunk_id += 1

            # The next slice advances while retaining the configured overlap.
            start += step_size

    # Completed chunk records are returned for inspection and embedding.
    return chunks

# The validated size and overlap settings are passed to chunk the extracted pages.
chunks = create_chunks(
    pages,
    CHUNK_SIZE,
    CHUNK_OVERLAP
)

# Keep the original encode interface while the selected model runs through the API.
class SeaLionEmbeddings:
    def __init__(self, model_name):
        self.model_name = model_name
        self.cache = {}

    def encode(self, texts, convert_to_numpy=True, normalize_embeddings=True,
               show_progress_bar=False):
        if not texts or any(not isinstance(text, str) or not text.strip() for text in texts):
            raise ValueError("Embedding input must contain nonempty text strings.")

        # Repeated questions reuse vectors from the same runtime and model.
        missing = list(dict.fromkeys(text for text in texts if text not in self.cache))
        for start in range(0, len(missing), 16):
            batch = missing[start:start + 16]
            result = sea_lion_request("embeddings", {"model": self.model_name, "input": batch})
            items = sorted(result.get("data", []), key=lambda item: item["index"])
            if [item["index"] for item in items] != list(range(len(batch))):
                raise RuntimeError("The embedding response does not match the input batch.")
            for text, item in zip(batch, items):
                self.cache[text] = item["embedding"]
            if show_progress_bar:
                print("Texts encoded:", min(start + len(batch), len(missing)), "/", len(missing))

        # Preserve input order so FAISS positions still match the chunk records.
        vectors = np.asarray([self.cache[text] for text in texts], dtype="float32")
        if vectors.ndim != 2 or vectors.shape[1] == 0 or not np.isfinite(vectors).all():
            raise RuntimeError("The API returned invalid embedding vectors.")
        if normalize_embeddings:
            lengths = np.linalg.norm(vectors, axis=1, keepdims=True)
            if np.any(lengths == 0):
                raise RuntimeError("Zero-length embeddings cannot be normalized.")
            vectors = vectors / lengths
        return vectors if convert_to_numpy else vectors.tolist()

Defining the Retrieval Function¶

retrieve_documents(query, top_k=3) compares a question with the indexed PDF chunks and returns the highest-scoring source records. The top_k=3 default is used only when the caller does not supply a result count; the test and session loop pass TOP_K explicitly. The query must be encoded with the same model as the document text so both sets of vectors can be compared. The first conditions reject an empty question and a nonpositive top_k because neither provides a useful search request. Encoding [query] creates a one-question batch, and the NumPy, normalization, and float32 settings match the document-vector preparation.

search_k = min(top_k, index.ntotal) avoids requesting more matches than the index contains. index.search(query_embedding, search_k) returns two arrays: the inner product scores and the matching vector positions. Because the question was passed as a one-item batch, indices[0] and scores[0] read the results for that question. The loop skips -1 positions because no valid chunk corresponds to that marker.

chunk_lookup[int(idx)] retrieves the source record, while results.append combines a one-based rank, chunk identifier, page, Python floating-point score, and text. rank + 1 gives a display rank starting from 1, while float(scores[0][rank]) changes the NumPy score to a Python number for the result dictionary. return results supplies the evidence to the retrieval test or rag_query. No minimum similarity threshold is applied, so a nonempty result list does not prove the PDF contains the answer; it only identifies the closest stored matches.

# The query and requested result count are accepted for vector search.
def retrieve_documents(
    query,
    top_k=3
):
    """
    Retrieve the top matching chunks using FAISS.

    Returns chunk ID, page, similarity score, and text.
    """

    # An empty question cannot provide a useful retrieval query.
    if not query or not query.strip():

        raise ValueError("The query cannot be empty.")

    # A positive retrieval count is required for the search.
    if top_k <= 0:

        raise ValueError("top_k must be greater than 0.")

    # The question uses the same model and vector format as the document.
    query_embedding = embedding_model.encode(
        [query],

        # NumPy arrays provide numerical input for the FAISS workflow.
        convert_to_numpy=True,

        # Unit-length vectors make inner product scores equal cosine similarity.
        normalize_embeddings=True
    )

    # float32 keeps the vector data type compatible with the FAISS search workflow.
    query_embedding = query_embedding.astype("float32")

    # The requested result count cannot exceed the stored vector count.
    search_k = min(top_k, index.ntotal)

    # FAISS returns similarity scores and positions for finding the source chunks.
    scores, indices = index.search(
        query_embedding,
        search_k
    )

    # The result list collects ranked matches with readable source details.
    results = []

    # The single query result list is visited in similarity order.
    for rank, idx in enumerate(indices[0]):

        # FAISS position -1 does not refer to a valid source chunk.
        if idx == -1:

            continue

        # The vector position is converted to an integer for source lookup.
        chunk = chunk_lookup[int(idx)]

        # The result keeps a one-based rank, source details, and a Python float score.
        results.append({
            "rank": rank + 1,
            "chunk_id": chunk["chunk_id"],
            "page": chunk["page"],
            "score": float(scores[0][rank]),
            "text": chunk["text"]
        })

    # Ranked matches are returned with scores and source details.
    return results

Ordering the Retrieved Documents¶

prioritize_documents sorts the records returned by retrieve_documents before create_rag_prompt adds the source text to the model input. The prompt builder may run out of tokens before including every retrieved chunk, so higher-scoring records need to be considered first. sorted(retrieved_documents, ...) returns a new list, and reverse=True places the largest scores first to match the normalized inner product search. result.get("score", float("-inf")) reads each record's FAISS score and uses negative infinity when the field is missing, placing that record after scored matches.

The function accepts question but does not inspect the question text or calculate a new relevance score. The returned order is therefore based on the existing FAISS scores, not a second model or keyword-ranking method. The prompt builder uses this order when selecting evidence.

def prioritize_documents(question, retrieved_documents):
    """
    Preserve FAISS similarity ranking.

    Assumes higher scores mean greater similarity,
    as with normalized embeddings and IndexFlatIP.
    """

    # Higher scores come first, with missing scores placed last.
    return sorted(
        retrieved_documents,

        key=lambda result: result.get("score", float("-inf")),
        reverse=True
    )

create_rag_prompt prepares the question and retrieved passages for the Qwen model. prioritize_documents keeps higher-scoring chunks first because the input budget may not hold every returned passage. prompt_prefix places the question under USER QUERY and the retrieved passages under CONTEXT BLOCK, keeping the two parts separate as shown in Lecture 9. Each passage receives a label containing the source filename, original PDF page, and chunk identifier. These labels let the generated citations point back to the selected circular rather than an unrelated benefit or page.

count_tokens(prompt_prefix + prompt_suffix) measures the fixed question, labels, system rules, and chat structure before evidence is added. Subtracting that count and the 128-token margin from the 4,096-token input budget gives the available evidence allowance. The loop measures each labeled source, accounts for separators, and keeps only the tokens that fit. If a source must be shortened, selection stops after that source so lower-ranked text cannot displace earlier evidence.

The selected text is decoded and joined into the final user prompt, with prompt_suffix adding the RESPONSE heading after the evidence. The system instructions remain in a separate API message, so the retrieved passages are presented as evidence for the answer. A second complete token count checks the assembled input because token boundaries can change after separate pieces are joined. If the prompt is still too long, the function stops rather than allowing silent input truncation.

The diagnostic output shows the actual selected evidence and token count, making missing passages visible before answer assessment. return prompt keeps the original interface used by rag_query.

# Build a question-and-evidence prompt while keeping the system rules separate.
def create_rag_prompt(question, retrieved_documents):
    ranked_documents = prioritize_documents(question, retrieved_documents)
    # Label the question and source passages so the model can distinguish each part.
    prompt_prefix = f"## USER QUERY\n{question}\n\n## CONTEXT BLOCK\n"
    # Mark the answer position after the evidence while keeping instructions in SYSTEM_PROMPT.
    prompt_suffix = "\n\n## RESPONSE\n"

    # The fixed count includes the system message and chat formatting.
    available_context_tokens = (
        MAX_INPUT_TOKENS - count_tokens(prompt_prefix + prompt_suffix) - RESERVED_TOKEN_MARGIN
    )
    if available_context_tokens <= 0:
        raise ValueError("The question and instructions leave no room for retrieved evidence.")
    selected_parts = []
    remaining_tokens = available_context_tokens

    # Higher-scoring source passages receive prompt space first.
    for result in ranked_documents:
        source_label = f"[Source: {pdf_file}; PDF page {result['page']}; Chunk {result['chunk_id']}]"
        source_text = f"{source_label}\n{result['text']}"
        source_tokens = tokenizer.encode(source_text, add_special_tokens=False)
        separator_tokens = tokenizer.encode("\n\n", add_special_tokens=False) if selected_parts else []
        tokens_available = remaining_tokens - len(separator_tokens)
        if tokens_available <= 0:
            break

        # Stop at token boundaries when the remaining evidence allowance is smaller than a source.
        included_tokens = source_tokens[:tokens_available]
        if not included_tokens:
            continue
        included_text = tokenizer.decode(
            included_tokens, skip_special_tokens=True, clean_up_tokenization_spaces=False,
        )
        # A source needs the complete label and at least some passage text to be useful.
        if source_label not in included_text or not included_text.split(source_label, 1)[1].strip():
            break
        selected_parts.append(included_text)
        remaining_tokens -= len(separator_tokens) + len(included_tokens)
        if len(included_tokens) < len(source_tokens):
            break

    if not selected_parts:
        raise ValueError("No labeled source passage fits the input budget.")
    context = "\n\n".join(selected_parts)
    prompt = prompt_prefix + context + prompt_suffix
    final_token_count = count_tokens(prompt)
    if final_token_count > MAX_INPUT_TOKENS:
        raise ValueError("The assembled chat input exceeds the experiment input budget.")

    # Show the evidence actually sent to generation, not only the full retrieval results.
    print("\n--- PROMPT DIAGNOSTICS ---")
    print("Retrieved chunks:", len(retrieved_documents))
    print("Chunks included:", len(selected_parts))
    print("Chat input tokens:", final_token_count)
    for i, part in enumerate(selected_parts, start=1):
        print(f"\nEvidence {i}:\n{part}")
    return prompt

def generate_answer(prompt, max_new_tokens=MAX_NEW_TOKENS):

    if max_new_tokens <= 0 or max_new_tokens > MAX_NEW_TOKENS:
        raise ValueError("The answer cap must stay within the fixed baseline output budget.")

        "messages": [

            {"role": "user", "content": prompt},
        ],
        "temperature": TEMPERATURE,
        "max_tokens": max_new_tokens,
        "chat_template_kwargs": {"enable_thinking": False},
    })
    choice = result["choices"][0]
    last_generation_metadata = {
        "local_input_tokens": input_length,
        "usage": result.get("usage", {}),
        "finish_reason": choice.get("finish_reason"),
        "model": result.get("model", LLM_NAME),

    print("Generation diagnostics:", last_generation_metadata)

    # A cut-off or empty response needs review before answer scoring.
    if choice.get("finish_reason") == "length":

    answer = choice.get("message", {}).get("content")
    if not isinstance(answer, str) or not answer.strip():
        raise RuntimeError("The API returned no readable answer; check model access and request settings.")
    return answer.strip()

Connecting the Complete RAG Query¶

rag_query(question, top_k=3) takes one question from the session loop, retrieves the PDF evidence, builds the prompt, and requests the answer from generate_answer. Combining retrieval, prompt construction, and generation here avoids repeating the same sequence inside the interactive loop. question.strip() removes edge whitespace, and a blank question returns a message with empty source and prompt values so the caller still receives three results.

retrieve_documents(question, top_k=top_k) fetches the matching records from the in-memory FAISS index created in Component I. If the result list is empty, the function returns the fallback message without calling the language model. This condition checks whether records were returned; it does not check whether nonempty records actually contain an answer.

create_rag_prompt builds the checked input from the question and retrieved records, then generate_answer produces the response. A further condition replaces a missing or whitespace-only answer with a review message so the display is not left blank. The final tuple contains the stripped answer, all retrieved records, and the exact prompt. The session loop uses the answer for display and keeps the sources and prompt for the inspection commands.

last_query_metadata keeps the retrieved sources and prepared prompt available if generation fails. The baseline run record can therefore retain the evidence needed to inspect an API error or a truncated answer without treating the failed run as a successful response.

# Retrieval, prompt construction, and generation run through one query function.
def rag_query(question, top_k=3):
    """
    General-purpose RAG question-answering function.

    Workflow:
    1. Retrieve relevant document chunks.
    2. Build a token-limited prompt.
    3. Generate an answer using the language model.
    4. Return the answer, retrieved sources, and prompt.
    """

    # Edge whitespace is removed before checking for an empty question.
    global last_query_metadata
    last_query_metadata = {"question": question, "sources": [], "prompt": ""}
    question = question.strip()

    # A blank question returns a message without running the model.
    if not question:

        # Return the response, available sources, and prompt in the expected format.
        return (
            "Please enter a valid question.",
            [],
            ""
        )

    # The nearest chunks supply evidence before prompt construction.
    retrieved_documents = retrieve_documents(
        question,
        top_k=top_k
    )

    # Generation is skipped when retrieval supplies no evidence.
    if not retrieved_documents:

        # Return the response, available sources, and prompt in the expected format.
        return (
            "I cannot find the answer in the provided document.",
            [],
            ""
        )

    last_query_metadata["sources"] = retrieved_documents

    # The question, instructions, evidence, and answer label form the model input.
    prompt = create_rag_prompt(
        question,
        retrieved_documents
    )

    # Request the answer from the evidence-based prompt and check for an empty response.
    last_query_metadata["prompt"] = prompt
    answer = generate_answer(prompt)

    # Missing or whitespace-only answers are replaced with a review message.
    if not answer or not answer.strip():

        # Request the answer from the evidence-based prompt and check for an empty response.
        answer = (
            "The model could not generate an answer. "
            "Please review the retrieved evidence."
        )

    # Return the response, available sources, and prompt in the expected format.
    return (
        answer.strip(),
        retrieved_documents,
        prompt
    )

Defining the Chunking Configurations¶

Each configuration is written as chunk size over overlap, both in characters. For example, 300/30 means chunks of up to 300 characters, where the last 30 characters of one chunk are repeated at the start of the next chunk. The overlap ratio is the overlap divided by the chunk size, so 300/30 has a 10% overlap.

The activity gives five configurations with fixed names, C1 300/0, C2 300/30, C3 300/60, C4 500/0, and C5 500/50, and asks each group to add seven more that fit its own dataset. The seven added here are C6 500/100, C7 750/0, C8 750/75, C9 750/150, C10 1000/0, C11 1000/100, and C12 1500/150. Most of them follow the same pattern as the given five, which use overlaps of 0%, 10%, and 20% of the chunk size. Using the same three ratios for 300, 500, 750, and 1,000 characters makes it possible to compare chunk sizes at the same overlap percentage, which Step 7 of the activity asks about. The 1,000/200 pair is left out of the list because it is the baseline, which runs separately in Step 1.

C12 uses 1,500 characters with 150 overlap. In Part 1, a 1,500-character chunk cut the FP001 implant row right after the code, before its fee amounts, so the chunk did not contain the answer. C12 checks whether a large chunk with 10% overlap still loses evidence in this way.

The list is built with two nested loops, one over the chunk sizes and one over the overlap ratios, which Step 3 of the activity suggests to reduce manual errors. The checks stop the notebook if any of the five given configurations is missing or has the wrong settings, if there are not exactly 12 configurations, or if an overlap is not smaller than its chunk size.

Defining the Implementation Checks¶

Step 3 of the activity lists checks that must pass before the results are used. check_chunks covers the chunking checks for every configuration. The overlap must be smaller than the chunk size, and no chunk can be longer than the chunk size. Every chunk must appear word for word inside the text of its own page. This proves that the chunk contains source text and that its page number is correct. Every page with text must produce at least one chunk, and the first chunk of each page must start at the beginning of the page. For pages longer than one chunk, the text shared by the first two chunks must appear in both. This proves that the overlap was applied with the correct length.

check_index covers the FAISS check. The number of stored vectors must equal the number of chunks. Three chunk vectors from the start, middle, and end of the list are searched in the new index, and each search must return the same chunk text. A match shows that the index was built from the current configuration and not from an earlier one. Any failed check raises an error and stops the run.

def check_chunks(chunks, pages, chunk_size, chunk_overlap):
    """Stop the run when the chunks do not follow the configuration or lose source text."""

    # The overlap must stay below the chunk size so the slicing loop moves forward.
    if not 0 <= chunk_overlap < chunk_size:
        raise ValueError("The overlap must be smaller than the chunk size.")

    # Chunks are grouped by page so each page can be checked separately.
    page_text = {page["page"]: page["text"] for page in pages}
    chunks_by_page = {}
    for chunk in chunks:
        chunks_by_page.setdefault(chunk["page"], []).append(chunk)

    problems = {
        # No chunk may be longer than the configured size.
        "too_long": [c["chunk_id"] for c in chunks if len(c["text"]) > chunk_size],
        # Each chunk must be an exact piece of its own page text.
        "not_in_page": [c["chunk_id"] for c in chunks if c["text"] not in page_text.get(c["page"], "")],
        # Every page with text must produce at least one chunk.
        "pages_without_chunks": sorted(set(page_text) - set(chunks_by_page)),
        "wrong_first_chunk": [],
        "overlap_not_shared": [],
    }

    step_size = chunk_size - chunk_overlap
    for page_number, text in page_text.items():
        page_chunks = chunks_by_page.get(page_number, [])
        if not page_chunks:
            continue

        # The first chunk must start at the first character of the page.
        if page_chunks[0]["text"] != text[:chunk_size].strip():
            problems["wrong_first_chunk"].append(page_number)

        # The text shared by the first two chunks must appear in both of them.
        if chunk_overlap > 0 and len(page_chunks) >= 2:
            shared = text[step_size:chunk_size].strip()
            if shared and not (shared in page_chunks[0]["text"] and shared in page_chunks[1]["text"]):
                problems["overlap_not_shared"].append(page_number)

    # Failed checks are reported with up to five examples each.
    failed = {name: found[:5] for name, found in problems.items() if found}
    if failed:
        raise RuntimeError(f"Chunk checks failed: {failed}")


def check_index(index, embeddings, chunks, chunk_lookup):
    """Stop the run when the FAISS index does not hold the current chunks."""

    # One vector must be stored for every chunk.
    if index.ntotal != len(chunks):
        raise RuntimeError("The number of vectors does not match the number of chunks.")

    # A stored chunk vector must find its own chunk text in the new index.
    for position in sorted({0, len(chunks) // 2, len(chunks) - 1}):
        _, found = index.search(embeddings[position:position + 1], 1)
        if chunk_lookup[int(found[0][0])]["text"] != chunks[position]["text"]:
            raise RuntimeError("The FAISS index does not match the current chunks.")

Defining the Evidence Matcher¶

The matcher decides whether a retrieved chunk contains an evidence unit, using the same rules for every configuration as Step 4 of the activity requires. A chunk only counts when it comes from one of the unit's allowed pages. The same fee row repeated in Annex D or Annex F does not count for a question about Annex B, even when the amounts are the same.

Each evidence unit in ground_truth uses one of two kinds of rules. A policy sentence, such as the claims filing rule on page 5, has a must_contain_all field with the key phrases of that sentence, and all of them must appear in the chunk. A fee table row, such as the FP001 implant row on page 222, has an anchors field with the procedure code or row label, and a values field with the amounts that must appear shortly after that code. A chunk that ends right after a code, such as one ending in FP001 SU, does not count because the amounts were cut off. Mentioning the same topic or keyword is not enough, which follows the relevance rule in Step 4.

The PDF text came from OCR, or optical character recognition, so it has small reading errors. The matcher handles the common ones. Spaces and punctuation are ignored when comparing phrases, thousands separators are ignored in amounts, and a colon is read as a comma because the OCR sometimes prints 5,850.00 as 5:850.00. Other known misreads, such as 1,756.00 printed for 1,755.00 in the ANC01 row, are listed in an ocr_variants field and were checked against the page images.

The last loop checks every evidence unit against the text of its own page. A failure would mean that ground_truth does not fit this PDF extraction, so the experiment stops before any configuration runs.

# Letters and digits are kept for phrase rules, so OCR spacing and punctuation are ignored.
def norm_alnum(text):
    return re.sub(r"[^a-z0-9]", "", text.lower())


# Amount rules read ':' as ',' and drop thousands separators before comparing numbers.
def norm_numeric(text):
    text = text.lower().replace(":", ",")
    text = re.sub(r"(?<=\d),(?=\d)", "", text)
    return re.sub(r"\s+", " ", text)


# An amount must match as a whole number, so 850.00 does not match inside 5850.00.
def value_pattern(value):
    escaped = re.escape(norm_numeric(value).strip())
    return re.compile(rf"(?<![\d.]){escaped}(?!\d)")


def match_unit(chunk_text, chunk_page, unit):
    """Return True when the chunk contains the evidence unit."""

    # Chunks from pages outside the allowed list never count.
    if unit.get("allowed_pages") and chunk_page not in unit["allowed_pages"]:
        return False

    # Every required phrase must appear in the chunk.
    alnum_text = norm_alnum(chunk_text)
    for phrase in unit.get("must_contain_all", []):
        if norm_alnum(phrase) not in alnum_text:
            return False

    # A unit without anchors is a phrase rule, which has passed at this point.
    anchors = unit.get("anchors", [])
    if not anchors:
        return True

    # A fee row counts when enough of its amounts appear in the window around its code or label.
    numeric_text = norm_numeric(chunk_text)
    needed = unit.get("min_values_matched", len(unit.get("values", [])))
    for anchor in anchors:
        for match in re.finditer(anchor["regex"], numeric_text):
            start = max(0, match.start() - anchor.get("before", 0))
            window = numeric_text[start:match.end() + anchor.get("after", 150)]
            found = 0
            for value in unit.get("values", []):
                forms = [value["value"], *value.get("ocr_variants", [])]
                if any(value_pattern(form).search(window) for form in forms):
                    found += 1
            if found >= needed:
                return True
    return False


# The IDs of the question's evidence units found in one chunk.
def units_covered(chunk_text, chunk_page, question):
    return [unit["id"] for unit in question["evidence_units"] if match_unit(chunk_text, chunk_page, unit)]

Defining the Retrieval Metrics¶

The metric functions follow Step 5 of the activity. question_metrics scores one question from its top 3 chunks. Precision@3 is the number of relevant chunks divided by 3. Recall@3 is the number of different evidence units found in the top 3 chunks divided by the number of evidence units of the question. One chunk can cover more than one unit, but a unit found by two chunks is counted once. The reciprocal rank is 1 divided by the rank of the first relevant chunk, so rank 1 gives 1.000, rank 2 gives 0.500, rank 3 gives 0.333, and no relevant chunk gives 0.000.

aggregate takes the mean of each score over all nine questions, and again for the Easy, Average, and Difficult questions. The overall MRR@3 is the mean reciprocal rank over all nine questions. It is not calculated by averaging the three difficulty-level MRR values, which Step 5 does not allow.

def question_metrics(relevant_flags, covered_units_per_rank, total_units):
    """Precision@3, Recall@3, and reciprocal rank for one question."""

    # Precision divides the relevant chunks in the top 3 by 3.
    flags = list(relevant_flags)[:TOP_K]
    precision = sum(flags) / TOP_K

    # A unit found by more than one chunk is counted once.
    covered = set()
    for units in list(covered_units_per_rank)[:TOP_K]:
        covered.update(units)
    recall = len(covered) / total_units

    # The rank of the first relevant chunk gives the reciprocal rank.
    reciprocal_rank = next((1 / rank for rank, relevant in enumerate(flags, start=1) if relevant), 0.0)
    return {"precision": precision, "recall": recall, "rr": reciprocal_rank, "covered_units": sorted(covered)}


def aggregate(question_rows):
    """Mean scores over all questions and for each difficulty level."""

    def mean_scores(rows):
        return {
            "precision": float(np.mean([r["precision"] for r in rows])),
            "recall": float(np.mean([r["recall"] for r in rows])),
            "mrr": float(np.mean([r["rr"] for r in rows])),
        }

    # The overall MRR uses all question reciprocal ranks, not the difficulty-level MRRs.
    scores = {"Overall": mean_scores(question_rows)}
    for level in ("Easy", "Average", "Difficult"):
        scores[level] = mean_scores([r for r in question_rows if r["difficulty"] == level])
    return scores

Defining the Experiment Run¶

run_configuration performs the ten steps listed in Step 3 of the activity for one configuration. It uses the PT-F1 code from Component I without changing it. CHUNK_SIZE and CHUNK_OVERLAP are set to the current configuration, create_chunks splits the same extracted pages, and embedding_model.encode creates the embeddings with the same settings as the PT-F1 embedding cell. A new faiss.IndexFlatIP is built from these embeddings, and chunk_lookup is rebuilt for the new chunks. retrieve_documents from Component I reads index and chunk_lookup, so both are replaced before any question is searched. This is how each configuration uses only its own new index.

The checks run in order. check_chunks runs before embedding, check_index runs after the index is built, and the question list is compared with QUESTION_TEXTS so every configuration uses the same nine questions. Each question then retrieves the top 3 chunks with TOP_K. Every chunk is labeled with the evidence units it contains, and the question is scored.

Step 8 of the activity asks to compare efficiency where it can be measured, so four values are recorded. Embedding time is how long the embedding step took. It mostly depends on the number of chunks, because every 16 chunks need one API request and requests are spaced 6.5 seconds apart. Index build time is how long FAISS took to store the vectors. Retrieval latency is the average time retrieve_documents took to return the top 3 chunks for one question. The question vectors are already stored, so this time covers only the FAISS search and not an API request. Index size is how many bytes the index would take if it were saved as a file, measured with faiss.serialize_index.

SeaLionEmbeddings from Component I keeps every vector it receives in embedding_model.cache, so the same text is not sent to the API twice. At the end of each configuration, this cache is cleared except for the nine question vectors. The next configuration then has to embed all of its chunks through the API, the same as the others, so the embedding times in Table A can be compared fairly.

def run_configuration(config):
    """Run Step 3 of the activity for one configuration."""
    global CHUNK_SIZE, CHUNK_OVERLAP, chunks, chunk_texts, embeddings, index, chunk_lookup

    # The heading identifies the configuration in the output.
    print("\n")
    print("=" * 70)
    print(f"RUNNING {config['label']}")
    print("=" * 70)

    # The PT-F1 setting names are reused so the Component I functions work unchanged.
    CHUNK_SIZE, CHUNK_OVERLAP = config["chunk_size"], config["chunk_overlap"]

    # Steps 3.1 and 3.2. The same extracted pages are split with this configuration and checked.
    chunks = create_chunks(pages, CHUNK_SIZE, CHUNK_OVERLAP)
    check_chunks(chunks, pages, CHUNK_SIZE, CHUNK_OVERLAP)

    # Step 3.3. The total number of chunks is recorded.
    print("Total chunks:", len(chunks))

    # Text stays in chunk order so embedding rows match the source records.
    chunk_texts = [chunk["text"] for chunk in chunks]

    # Step 3.4. The chunks are embedded with the same model and settings as Component I.
    started = time.perf_counter()
    embeddings = embedding_model.encode(
        chunk_texts,
        convert_to_numpy=True,
        normalize_embeddings=True,
        show_progress_bar=True
    )
    embeddings = embeddings.astype("float32")
    embedding_seconds = time.perf_counter() - started

    # Step 3.5. A new flat inner product index is built for this configuration only.
    started = time.perf_counter()
    index = faiss.IndexFlatIP(embeddings.shape[1])
    index.add(embeddings)
    index_build_seconds = time.perf_counter() - started

    # Vector positions map back to this configuration's chunk records.
    chunk_lookup = {position: chunk for position, chunk in enumerate(chunks)}
    check_index(index, embeddings, chunks, chunk_lookup)
    index_size_bytes = int(faiss.serialize_index(index).size)

    # The same nine questions must be used for every configuration.
    if [ground_truth[qid]["question"] for qid in QUESTION_IDS] != QUESTION_TEXTS:
        raise RuntimeError("The question list changed between configurations.")

    # Steps 3.6 to 3.9. Each question retrieves the top 3 chunks, which are labeled and scored.
    question_rows, latencies = [], []
    for qid in QUESTION_IDS:
        question = ground_truth[qid]
        started = time.perf_counter()
        retrieved = retrieve_documents(question["question"], TOP_K)
        latencies.append(time.perf_counter() - started)

        for result in retrieved:
            result["covered_units"] = units_covered(result["text"], result["page"], question)
            result["relevant"] = len(result["covered_units"]) > 0

        scores = question_metrics(
            [result["relevant"] for result in retrieved],
            [result["covered_units"] for result in retrieved],
            len(question["evidence_units"])
        )
        question_rows.append({"question_id": qid, "difficulty": question["difficulty"],
                              "retrieved": retrieved, **scores})

    # Only the question vectors stay in memory, so the next configuration embeds its chunks from the start.
    embedding_model.cache = {text: embedding_model.cache[text] for text in QUESTION_TEXTS}

    # Step 3.10. The settings, efficiency values, retrieved records, and scores are kept together.
    result = {
        **config,
        "total_chunks": len(chunks),
        "embedding_seconds": embedding_seconds,
        "index_build_seconds": index_build_seconds,
        "mean_retrieval_latency_ms": 1000 * float(np.mean(latencies)),
        "index_size_bytes": index_size_bytes,
        "questions": question_rows,
        "scores": aggregate(question_rows),
    }
    overall = result["scores"]["Overall"]
    print(f"Precision@3: {overall['precision']:.3f}   Recall@3: {overall['recall']:.3f}   MRR@3: {overall['mrr']:.3f}")
    return result

The tables follow Step 6 of the activity. Table A has one row per configuration with the chunk size, overlap, total chunks, Precision@3, Recall@3, and MRR@3. The efficiency columns, embedding time, index build time, retrieval latency, and index size, are added because Step 8 asks for them where they can be measured. Table B has three rows per configuration, one for each difficulty level. Table C is the detailed retrieval log with one row for every retrieved chunk. It has the configuration, question ID, difficulty, expected evidence units, rank, chunk ID, source reference, relevant label, evidence covered, and the chunk text that was retrieved.

The baseline is the first row in each table so the other configurations can be compared with it. The annex name in the source reference comes from the page ranges in ANNEX_PAGE_MAP.

Analyzing the Results¶

The ten analysis questions in Step 7 of the activity are answered below using Table A, Table B, and Table C. Every score is an average over the nine test questions, so a small difference between two configurations can come from just one question. Since each configuration retrieves 27 chunks in total, one more relevant chunk raises Precision@3 by 0.037. One question moving from no relevant chunk to a relevant chunk at rank 1 raises MRR@3 by 0.111. The scores in Table B come from only three questions per difficulty level, so one question can change them by up to 0.333.

Precision@3 is low for every configuration, between 0.148 and 0.296. Most questions have only one or two evidence units, and each unit is usually found in just one chunk. If only one chunk has the evidence, the highest possible Precision@3 for that question is 0.333. For this reason, the scores are compared between configurations and not against 1.0.

1. Highest Precision@3¶

C4 (500/0) has the highest Precision@3 at 0.296. This means 8 of its 27 retrieved chunks contained evidence. C5, C8, C9, C11, and C12 follow at 0.259, or 7 of 27, and the baseline has 0.222, or 6 of 27. C2 (300/30) has the lowest Precision@3 at 0.148, or 4 of 27. C4 is ahead of the next group by only one relevant chunk.

2. Highest Recall@3¶

C4 (500/0) also has the highest Recall@3 at 0.556. Most of this lead comes from Q09, a difficult question with three evidence units. For Q09, C4 retrieved the three needed clauses from pages 3, 4, and 5 at ranks 1, 2, and 3, so all three units were found. C5, C9, C10, C11, and C12 follow at 0.519, and the baseline has 0.463. C2 (300/30) again has the lowest score at 0.278.

3. Highest MRR@3¶

C5 (500/50) has the highest MRR@3 at 0.667. C5 found evidence for six questions, Q02, Q04, Q05, Q06, Q07, and Q09, and for all six the first relevant chunk was at rank 1. It found no evidence for Q01, Q03, and Q08, so its MRR@3 is 6 divided by 9. C12 (1500/150) follows at 0.611 and C3 (300/60) at 0.593. The baseline and C7 both have 0.426, and C2 has the lowest MRR@3 at 0.370.

4. Agreement Between the Metrics¶

Not fully. C4 has the best Precision@3 and Recall@3, but its MRR@3 of 0.537 is only seventh out of the thirteen runs. This is because its first relevant chunk was at rank 3 for Q02 and at rank 2 for Q07. C5 has the best MRR@3, but it is in the second group for Precision@3 at 0.259 and Recall@3 at 0.519. C5 and C12 are near the top on all three metrics. They have the same Precision@3 and Recall@3, and their MRR@3 values are 0.667 and 0.611. No configuration was the best on all three metrics.

5. Best Chunk Size at the Same Overlap Percentage¶

With 0% overlap, 500 characters (C4) had the best Precision@3 and Recall@3 among 300, 500, 750, and 1,000 characters. The 300-character run (C1) had a slightly higher MRR@3 of 0.556 compared to 0.537. With 10% overlap, 500 characters (C5) had the best MRR@3 of 0.667. Its Precision@3 of 0.259 was tied with 750, 1,000, and 1,500 characters, and its Recall@3 of 0.519 was tied with 1,000 and 1,500 characters. With 20% overlap, no size was best on all metrics. C9 (750 characters) had the best Precision@3 and Recall@3 at 0.259 and 0.519, and C3 (300 characters) had the best MRR@3 at 0.593.

Looking at all three overlap ratios, 500 characters gave the best results. The 300-character chunks had the lowest Recall@3 at every ratio, with 0.370, 0.278, and 0.426.

6. Effect of Increasing Overlap¶

Adding overlap increased the number of chunks every time. A 10% overlap produced about 10% to 12% more chunks, and a 20% overlap produced about 23% to 24% more chunks than the same size with no overlap. For example, the 500-character runs went from 2,642 chunks with no overlap to 2,919 with 10% and 3,281 with 20%. Their embedding time also went up from 1,073 to 1,189 and then 1,339 seconds.

The retrieval scores did not go up in the same way. At 300 characters, the 10% overlap (C2) had the weakest result in the experiment, but the 20% overlap (C3) had the best MRR@3 for that size. At 500 characters, no overlap had the best Precision@3 and Recall@3, 10% overlap had the best MRR@3, and 20% overlap (C6) was lower on all three metrics. At 750 characters, both overlaps did better than no overlap, and Recall@3 went up from 0.407 to 0.481 and 0.519. At 1,000 characters, 10% overlap raised MRR@3 from 0.444 to 0.556, but the 20% overlap of the baseline lowered Recall@3 from 0.519 to 0.463. Overlap can keep a sentence complete across a chunk boundary, but it also creates repeated text and extra cost. In this experiment, more overlap always meant more chunks, but it did not always mean better retrieval.

7. Best Configuration for Difficult Questions¶

C4 (500/0) had the best Precision@3 and Recall@3 on the difficult questions, both at 0.333. This is because it was the only configuration that retrieved all three evidence units of Q09. C3 (300/60) had the best difficult-question MRR@3 at 0.667. C3 was also the only configuration that retrieved the MCP01 row in Annex B for Q08 (Q08-E1), and it ranked that row first.

All configurations scored lowest on the difficult questions. No configuration retrieved any evidence unit of Q03, which needs two procedure rows from Annex B and the claims filing rule on page 5. The MCP01 row in Annex F for Q08 (Q08-E2) was also never retrieved. C2 (300/30) scored 0 on all three difficult questions.

8. Smaller Chunks, Focused Evidence or Fragmented Information¶

Both happened in the 300-character runs. For the average questions, the small chunks ranked focused evidence well. C1 (300/0) ranked the evidence first for Q02, Q06, and Q07 and reached an average-question MRR@3 of 1.000. C3 (300/60) was the only run that found the short MCP01 fee row for Q08.

Small chunks also split sentences that the answer needs. In C1, the top chunk for Q04 ends with "shall take effect on hospital admis", so the date of effectivity is not in the chunk and Q04 was missed. In C2, the chunks retrieved for Q09 start in the middle of the needed sentences, such as "mount indicated in the rate schedule". Because of this, no evidence unit was complete, and all three difficult questions scored 0. The 300-character runs also had the lowest Recall@3 at every overlap ratio. Based on these results, the small chunks split more evidence than they helped to rank for this circular.

9. Larger Chunks, Useful Context or Irrelevant Information¶

Both happened as well. Larger chunks kept useful context for some questions. In C10 (1000/0), one chunk from page 222 contained both the 58300 IUD row and the FP001 implant row, so Q02 got full recall from a single chunk at rank 1. C10, C11, and C12 all reached a Recall@3 of 0.519.

Larger chunks also brought in text that does not answer the question. In C10, the top part of page 1, which only has the PhilHealth name, address, and circular number, was ranked above the effectivity clause for Q04. Because of this, the correct chunk dropped to rank 2. The easy-question MRR@3 dropped to 0.500 in C9, C10, and C11, compared to 0.667 for most other runs. Precision@3 also did not go up with size and stayed between 0.222 and 0.259 for 750 characters and above. In Part 1, a 1,500-character chunk cut the FP001 row before its amounts, and in this experiment no configuration of any size retrieved the FP001 row for Q01.

10. Similar Quality With Different Numbers of Chunks¶

Yes. C5 (2,919 chunks), C9 (2,236), C11 (1,543), and C12 (1,079) all have a Precision@3 of 0.259 and a Recall@3 of 0.519. C12 uses about 37% of the chunks of C5, takes 442 seconds to embed compared to 1,189 seconds, and has an index of 4.4 MB compared to 12.0 MB. Their MRR@3 values are 0.667 and 0.611, and this difference of 0.056 comes from only one question, Q07, where C12 ranked the evidence second instead of first.

The baseline (1,707 chunks) and C6 (3,281 chunks) also have the same Precision@3 of 0.222 and Recall@3 of 0.463. C6 used almost twice as many chunks as the baseline but did not find more evidence.

Determining the Best Configuration¶

Based on the results, the recommended configuration for PhilHealth Circular 2024-0037 is C4, with a chunk size of 500 characters, no overlap, and Top-K kept at 3. This choice follows the five points in Step 8 of the activity. For retrieval quality, C4 has the highest Precision@3 at 0.296 and the highest Recall@3 at 0.556, so it gave the best recall without losing precision. For question difficulty, it tied for the best easy-question scores, tied for the best average-question Recall@3 of 0.667, and had the best difficult-question Precision@3 and Recall@3. For evidence completeness, it has the highest Recall@3 and is the only run that found all three evidence units of a three-unit question. For efficiency, its 2,642 chunks are fewer than those of C5, C6, and every 300-character run, with an embedding time of 1,073 seconds and an index of 10.8 MB. For consistency, it found evidence for six of the nine questions, which ties the highest count.

C5 (500/50) has a better MRR@3 than C4, at 0.667 compared to 0.537. This is because C5 ranked the first relevant chunk at rank 1 for every question it found. In the BenepiKnow pipeline, all three retrieved chunks are given to the language model, and three 500-character chunks fit within the 4,096-token prompt limit. Because of this, retrieving the evidence anywhere in the top three is more important than ranking it first, and this gives C4 the advantage because it had the higher recall. C12 (1500/150) is the most efficient run with similar scores. However, it found less evidence for the difficult questions than C4, with a Recall@3 of 0.222 compared to 0.333, and Part 1 showed that 1,500-character chunks can cut a fee row before its amounts.

The difference between the top configurations is small. C4 is ahead of the next group by one relevant chunk in Precision@3 and one evidence unit in Recall@3. The results show that 500 characters is the best chunk size for this circular, but they do not show that no overlap is better than an overlap of 50 characters. Q01 and Q03 were not answered by any configuration, and Q08 was answered only once. These questions ask about short fee rows inside more than 270 pages of similar tables, and changing the chunk size did not fix them. This suggests that the problem comes from how the embedding model searches long tables of numbers and not from the chunk settings. To confirm the choice, a larger test should be done with more questions for each difficulty level, chunk sizes between 400 and 600 characters, and overlaps between 0 and 50 characters. Structure-aware chunking, which splits the annex tables by row instead of by character count, should also be tested.
